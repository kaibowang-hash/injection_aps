## 3. 实现结果

### 3.1 Demand Commitment 和跨 Run 所有权

- 新增 `APS Demand Commitment`，记录 Run、Demand Identity、P0/P1/P2、Owned/Referenced/Superseded/Conflict/Released、Frozen/Carried/Reschedulable/Completed/Excess 和数量快照。
- 数据库 `active_owner_key` 唯一约束保证同一 Demand Identity 只能存在一个生效 Formal owner；公司锁、来源 Commitment 行锁和幂等键共同保护转移事务。
- Frozen 旧 Run 保持所有权，新 Trial 仅 Reference；可调任务可在内部受控入口原子 Transfer，原记录改为 Superseded。
- 已开工、已有产出、Scheduling 已开始或显式 `custom_aps_locked_for_reschedule=1` 的工单均分类为 Frozen。
- Work Order 血缘部分缺失时只计算可验证工单的剩余供应；全部声明的工单均缺失时最多沿用已审计 `carried_qty`，不会把整笔需求 `remaining_qty` 冒充供应。未解析工单名继续写入血缘供人工审计。
- Completed 和 Excess 生成独立终态 Commitment，`newly_planned_qty=0`、`remaining_qty=0`；Excess 不再作为原需求未完成量。

### 3.2 成品库存覆盖和数量守恒

- 新增 `APS Stock Coverage Allocation`；同一公司内使用公司行锁和稳定顺序“原交期 → 有效交期 → 服务优先级 → Identity”分配有限成品库存。
- 可分配库存为实际库存减销售/库存预留、生产/委外/生产计划预留和其他生效 APS claim。
- `new_plan_qty=max(schedule_open-stock_covered-carried_remaining,0)`；Produced 入库后只通过成品库存覆盖，不再同时作为额外 carried supply。
- 每条 P0 验证 `requested=stock_covered+carried+newly_planned`，并核对库存覆盖明细合计。

### 3.3 P0/P1/P2 准入

- 新增 `APS Demand Admission`。P0 自动全选并锁定；P1/P2 候选默认 0，只有 PMC/计划角色保存带理由的选择后才形成 Trial proposed Commitment。
- P1 为 `open SO - open schedule - active Formal Owned P1`；Trial 选择和 Referenced 镜像不会抑制其他 Run，也不会重复扣 Formal 来源。
- P2 为安全库存目标减预计未分配成品库存。
- 保存 P1/P2 时验证乐观指纹、记录决策人/时间/理由，并清除旧产能平衡状态和指纹，强制重新分析。
- Public API 禁止本阶段 Formal V2 ownership 写入；Formal Transfer 只保留给后续受控内部发布流程。

### 3.4 UI、API 和权限

- 新增 `Demand Admission Workbench`：显示 P0、库存覆盖、承接、新计划、P1/P2 候选，P0 输入锁定，P1/P2 可选，所有禁用动作有说明。
- Run Console 仅在 V2 Flag 开启时显示 Demand Admission、Carry Forward 和 Source Run 信息；Flag Off 不增加旧页面操作。
- Prepare、Preview、Save API 均校验 APS 角色和 Run record scope；写接口仅允许 POST，JSON 数组有类型和行数上限。
- 三个辅助 DocType 对业务角色只读，用户不能直接新增、修改或删除 engine-managed 台账。
- 新增界面、消息、字段和状态均已补齐中文翻译；翻译键唯一且占位符一致。

## 4. 实现结果

### 4.1 Revision 和 Demand Identity

- 新增 `APS Demand Identity`，并在 Schedule Header/Item 保存 revision mode、推荐、确认审计、稳定身份、原始/有效日期、有效数量、执行下限、Excess 和 open revised qty。
- Full Replacement 取消遗漏身份；Partial Revision 只替换触及身份并保留其他身份；Incremental Demand 始终创建独立身份。
- 匹配优先使用 Demand Identity、外部行 ID、上一排期行/日期，再使用唯一业务候选；多义结果阻塞 Apply，禁止猜测。
- 请求指纹与 active-state concurrency token 分离，精确重试可幂等重放，预览后并发变化会被阻止。
- 新版导入 UI 显示推荐模式和理由，要求显式确认；偏离推荐必须填写原因。Flag Off 时不改变旧快照、指纹或控制器路径。

### 4.2 Delivery 和既有生产流程

- 新增 `APS Unallocated Delivery` 独立队列；无链接或歧义只进入队列，不阻塞 ERPNext 出货。
- 明确血缘顺序为 DN Identity → Delivery Plan → 旧 Schedule Item → Legacy Controlled Match；Legacy 只分配可用 open qty，余量进入队列。
- Delivery Plan Qty 的身份可传播到完整覆盖的 SO Item，再继承到 DN Item；提交 DN 才计 delivered，退货沿原 Allocation 反冲。
- APS 自动 DP helper 已按 customer/company/date/address 分组；未把它接入新自动步骤，现有“工单→工单排产→入库→出货计划分配订单→下推销售出库”操作保持不变。
- V2 下无 SO 的 APS 需求可创建 Work Order；有 SO 时仍保留原 SO 血缘。
- 外部 DocType 新字段全部为隐藏、非必填；既有 `Delivery Note Item.custom_aps_customer_schedule_item` 不重新定义、不覆盖属性。

### 4.3 API、权限和事务

- 新增推荐、Revision 预览/应用、身份消歧和 Unallocated Delivery 处理 API；所有变更接口均限制为 POST，并复用 company/customer/document scope 权限。
- “应用 Revision + 可选需求重建”在同一请求事务内执行；重建额外要求 APS Plan 权限和完整 company scope。
- Active Schedule 仍只允许受控导入服务修改；Identity、Allocation 和 Queue 的更新只走受控服务。
